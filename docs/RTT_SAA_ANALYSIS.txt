What RTT Checks Would Do

Purpose: Measure network latency/round-trip time and alert if too high.

Use Cases:
  - VoIP/video quality monitoring (need <150ms for good voice)
  - WAN link performance
  - Database connection latency
  - API response time monitoring
  - Gaming server latency

Example Configuration:
`
object wan-link {
    ip "remote-office.example.com";
    type rtt;
    rtt_threshold 100;   # Alert if RTT > 100ms
    contact "netops@example.com";
};
`

Implementation Approaches

Option A: ICMP-Based (Built-in)

How it works:
  - Send ICMP echo request with timestamp in payload
  - Measure time from send to receive reply
  - Calculate RTT in milliseconds
  - Alert if exceeds threshold

Advantages:
  - ? No external dependencies
  - ? Uses existing ICMP infrastructure
  - ? Simple to implement
  - ? Works through most firewalls

Disadvantages:
  - ? ICMP may be deprioritized by routers
  - ? Not application-layer measurement
  - ? Doesn't reflect actual service performance

Similar to: Existing PING check but with latency measurement

Option B: UDP-Based (External Agent)

What WISHLIST suggests: "use external rtt agent?"

How it works:
  - External agent (daemon) runs on remote host
  - Sysmon sends UDP packet with timestamp
  - Agent reflects packet back (echo service)
  - Sysmon measures round-trip time

Advantages:
  - ? More accurate than ICMP
  - ? Bidirectional measurement
  - ? Can test specific ports
  - ? Reflects network path for UDP apps

Disadvantages:
  - ? Requires agent installation on remote hosts
  - ? Additional maintenance burden
  - ? Firewall configuration needed
  - ? Agent availability = single point of failure

Similar to: SYSM_TYPE_UDP_RTT (type 21) - appears to be this concept

Option C: TCP-Based (Application-layer)

How it works:
  - Measure time to complete TCP 3-way handshake
  - Connect to specific service port
  - Calculate connection establishment time
  - Alert if too slow

Advantages:
  - ? Application-layer measurement
  - ? Tests actual service reachability
  - ? No external agent needed
  - ? Reflects real user experience

Disadvantages:
  - ? Slower than ICMP/UDP
  - ? May trigger service logs/alarms
  - ? Some services rate-limit connections

Implementation: Enhance existing TCP check with timing

Recommended Approach

Phase 1: ICMP RTT (Built-in)
  - Extend existing PING code
  - Add RTT calculation using gettimeofday()
  - Add rtt_threshold configuration
  - ~8-12 hours implementation

Phase 2: TCP Connection Timing
  - Measure existing TCP check latency
  - Add threshold checking
  - ~4-6 hours implementation

Phase 3: UDP External Agent (Optional)
  - Only if users request it
  - Requires agent development
  - ~40+ hours implementation

2. SAA (Service Assurance Agent)

What is SAA?

Cisco SAA (now called IP SLA - Service Level Agreement):

A feature in Cisco routers/switches that performs:
  - Jitter measurement (packet delay variation)
  - Packet loss measurement
  - Round-trip time measurement
  - Path tracing
  - VoIP quality metrics (MOS score)
  - HTTP/FTP response time

SAA agents run on Cisco devices and can:
  - Measure between router pairs
  - Test specific applications
  - Generate synthetic traffic
  - Collect detailed statistics

Current Status in Sysmon

  - ? No SAA support whatsoever
  - ? No SAA-related code
  - ? No SAA configuration keywords
  - ? No integration with Cisco devices

Why "SAA?" with Question Mark?

The WISHLIST author was likely asking:
1. Should sysmon integrate with Cisco SAA/IP SLA?
2. Should sysmon implement its own SAA-like functionality?
3. Is there demand for this feature?

Integration Approaches

Option A: Query Cisco IP SLA via SNMP

How it works:
  - Cisco routers run IP SLA tests
  - Results stored in SNMP MIBs
  - Sysmon queries SNMP for results
  - Alert based on thresholds

Advantages:
  - ? Leverage existing Cisco infrastructure
  - ? No additional agents needed
  - ? Professional-grade measurements
  - ? Cisco maintains the feature

Disadvantages:
  - ? Requires Cisco equipment
  - ? Complex SNMP MIB structure
  - ? Limited to Cisco devices
  - ? Requires IP SLA configuration knowledge

Complexity: High (SNMP MIB parsing, Cisco-specific)

Option B: Implement SAA-like Features

What to implement:
  - Jitter measurement (packet delay variation)
  - Consecutive packet loss
  - Path MTU discovery
  - VoIP quality metrics

Advantages:
  - ? Vendor-independent
  - ? Flexible configuration
  - ? Integrated with sysmon

Disadvantages:
  - ? Massive development effort
  - ? Duplicates existing tools
  - ? Requires deep networking knowledge
  - ? Maintenance burden

Complexity: Very High (100+ hours)

Option C: External Tool Integration

How it works:
  - Use existing tools (smokeping, iperf, etc.)
  - Sysmon parses their output
  - Alert based on results

Advantages:
  - ? Leverage mature tools
  - ? Less development
  - ? Best-of-breed features

Disadvantages:
  - ? External dependencies
  - ? Multiple config files
  - ? Output parsing fragility

Complexity: Medium (20-30 hours)

Questions to Answer

Before implementing RTT/SAA features:

1. What latency thresholds matter to users?
  - Web: 200-500ms
  - VoIP: 100-150ms
  - Gaming: 50-100ms
  - Database: 10-50ms

2. Is ICMP RTT sufficient or need application-layer?
  - ICMP: Fast, simple, may not reflect app performance
  - TCP: Slower, reflects actual service

3. Do users have Cisco equipment for SAA?
  - If yes: SNMP integration
  - If no: Build own features

4. What's more valuable: RTT or Jitter?
  - RTT: General latency
  - Jitter: VoIP/video quality

5. Alerting granularity?
  - Single threshold
  - Multiple levels (warning/critical)
  - Trend-based alerts
